## 规模与性能

实际测试环境为 Docker Linux，6 个可用 CPU、约 11.68 GiB 内存；应用使用受限 NOBYPASSRLS 角色和 PostgreSQL 17.11。它小于计划的 8 vCPU／32 GB 参考环境，也不是最低安装要求。

数据为 100,000 个对象、1,000,000 条关系、50 个不同用户。50 个并发客户端共执行 1,000 次实际 HTTP 请求：350 次全文检索、350 次邻域分页、300 次对象详情。检索和匹配索引由合成夹具预建，此项测量不代表首次接入或全量建索引速度。

单 API 进程、独立压测客户端的测量：

| 请求 | P50 | P95 | 结果 |
| --- | ---: | ---: | --- |
| 全文搜索 | 1.198 s | 2.563 s | 超过 1 s 目标 |
| 邻域分页 | 0.935 s | 1.380 s | 超过 1 s 目标 |
| 对象详情 | 0.828 s | 1.169 s | 超过 1 s 目标 |

本轮 1,000 次请求全部成功。10 万对象的后台模型校验为 402 批、98.84 s；20 次顺序对象修改经真实 worker 同时传播到检索和规则关系，P95 为 0.387 s。这个传播结果不是 50 个并发写入者的压力测试。

最初检测到 RLS 下旧全文表达式扫描整租户索引表。复用派生表改为规范化词项等值索引后，实际 PostgreSQL 执行计划使用 Index Only Scan，示例计数查询执行约 0.234 ms。租户／字段权限没有放宽。早期把负载生成器与 API 放在同一 Python 进程的结果不用于最终验收。

后续同一 API 服务的多进程测量尚在执行；没有据单进程结果宣布查询目标已达标。

复现方式（先提供专用测试 PostgreSQL 的两个环境变量，不要指向生产库）：

```sh
python scripts/beta_benchmark.py --objects 100000 --relations 1000000 --users 50 --workers 1
```

工具创建并删除随机命名的独立测试数据库；客户端与 API 分属不同进程。原始结果默认位于 `var/beta-benchmark.json`。

## 部署与恢复

实际 Linux Compose 验证已通过：production 配置、Secure Cookie、受限数据库角色、异人审批、真实采集 worker、健康检查、任务指标、独立空库／空卷恢复及原始文件字节一致性。

最终小夹具测得备份 3.17 s、恢复到可登录并读取对象／原件 22.31 s。它只有一份 CSV 和一个对象，不能推断百万关系或大体积附件的恢复时间。完整规模的合成数据恢复单独记录。

```sh
docker build -t ontweft:beta-test .
python scripts/verify_deployment.py
python scripts/verify_deployment.py --scale
```

RPO 仍取决于部署者实际执行的备份频率和完成时间；当前工具没有自动备份调度，也未据一次恢复声称达到生产 RPO。

## 尚未宣称通过

- 8 vCPU／32 GB 专用参考机上的正式性能验收、长时间持续负载、并发写入传播与不同数据分布。
- 大体积文档／附件集的恢复和真实灾难条件；仅数据库合成规模不能替代它们。
- 真实飞书员工授权、外发和复杂 OCR；需要分别配置和验收。
- 完整 OWL／SHACL、通用推理、向量及自然语言查询。这些仍按实际用例后续推进，核心不依赖它们。
- 商标清查、完整安全审计及所有第三方二进制／模型包的再分发验收。
