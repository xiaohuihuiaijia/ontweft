## 待审核：需要范围、语义或兼容性决策

下面各项均未冒充已修复。优先级指下一步顺序，不表示所有部署已出现故障。

### 1. CDC 的重建基线入口缺失 — 高

`cdc/projection.py` 会在模型/来源基线不匹配时停止，`projection_api.py` 的绑定不可变，`api.py` 又禁止同一来源新建第二条流；现有操作只有暂停、恢复和换令牌。网络中断后的同基线续传已覆盖，不能据此声称能处理所有重建基线场景。本次已纠正文档。

建议：增加一条明确的“新绑定代＋重建基线”迁移路径，保留旧绑定、窗口和证据；只让实际涉及的模型变更失效绑定。需要先审核绑定版本、旧贡献撤回及失败切换边界，不能直接改写旧绑定或重放到当前对象。

### 2. 性能目标尚未全部达到 — 高

已有 10 万对象／100 万关系、50 用户测量中，唯一编码搜索 P95 为 1.176s，首轮 1.911s，超过 1s 目标；6 CPU／11.68 GiB 环境不等于计划参考机。常见词大结果集、50 并发写入传播及首次全量索引仍未覆盖。

建议：先在专用参考环境测真实查询分布和并发写入，依据 SQL/锁/CPU 的实测占比优化；此时不引入新的搜索服务或消息基础设施。

### 3. 数值键的计算上限与时间键的相等语义 — 高

`objects/constraints.py:number_text` 对有限 Decimal 使用固定小数展开；极短的巨大指数输入会要求生成极长字符串。当前输入允许有限数值，没有相应精度/指数预算。唯一键中的时间值仍按表示形式参与摘要，而匹配流程有类型规范化，等价时区表示可能产生不同键。

建议：先明确业务允许的数值精度/指数、日期与时间相等语义，再在共享边界规范化，并为已有键提供重建/冲突预览。不能直接改摘要算法，否则已有唯一键和身份关联会发生兼容变化。

### 4. 长事务中的采集与网络 I/O — 中

`sources/ingestion.py:project_snapshot` 的最终投影在一个项目写事务中遍历全部记录；分批读取不等于分批提交。部分来源探测操作在持有项目锁时访问外部来源，慢连接可能拖住同项目其他写入。目前这是代码层面的阻塞风险，尚无本轮实测延迟结论。

建议：先测大批量导入及慢来源下的锁等待；按证据决定是否将网络读取移到事务外、最终复核修订，或为投影增加分批检查点。后者涉及“整批原子提交还是分批可见”的产品选择。

### 5. 登录限流是进程内状态 — 中

`identity/api.py` 的失败计数只在同一键再次访问时过滤时间，其他过期键没有回收；不同进程之间不共享，读改写也不具备原子性。多用户名尝试可积累内存，多进程下不能当作统一的登录速率上限。

建议：补有界过期回收与单进程并发保护，并明确由现有反向代理承担实例级入口限流，或使用现有 PostgreSQL 共享计数。二选一；不因此添加 Redis 或独立安全平台。

### 6. 文件与历史列表的生命周期 — 中

新版本的失败写入已修，但成功预览、未应用版本和历史证据仍长期保留；已有遗留孤儿文件也没有依据可安全自动删除。版本接口目前仅返回最近 100 条，没有继续翻页；更早原件按 ID 仍可访问。

建议：先定“保留全部证据还是允许按策略归档”，补游标分页和可解释的占用统计；任何清理先给出引用核对及清单。未批准策略前不删历史文件。

### 7. 图谱编辑后的展开来源信息 — 低

`useGraphExploration.refresh` 正确重读当前授权节点，但把多个展开切片合为恢复视图，原节点的“收起邻域”来源和分页游标随之丢失。数据、固定点和坐标保留，交互连续性仍可改进。

建议：若需要“编辑后还能逐个收起原展开层”，保存有限的展开来源并重建各切片；如果产品接受刷新作为当前视图的新起点，明确这个行为即可。无需增加跨会话图谱状态平台。

建议优先处理 1、3，再进行 2、4 的测量；5、6 纳入部署与存储边界，7 按实际使用反馈决定。飞书、OCR、语义与 AI 的独立验收继续保持按需，不为本次清理扩大核心。
