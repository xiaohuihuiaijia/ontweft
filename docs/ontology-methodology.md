# 从业务问题到可运行本体

本方法用于序枢现有 Python / React 平台的建模、接入、验证和展示。本方法以已实现的类型、组合唯一键、关系基数和审批约束为基础；推理、双时态或自然语言查询仍不作为已有能力。

## 一、用业务问题限定边界

先写用户需要回答的 3–5 个问题，再决定需要哪些类型。每个问题同时记录输入、期望答案、所需来源、可见角色和不能确定时的行为。例如：

| 问题 | 所需结构 | 验证方式 |
| --- | --- | --- |
| 一个项目有哪些任务？ | 项目、任务、任务→所属项目→项目 | 建立两个不同项目与任务，核对关系方向及项目筛选 |
| 任务的计划完成日期是什么？ | 任务的日期属性 | 日期无值时显示缺失，不能推断已经完成 |
| 某处存放了哪些资产？ | 位置、资产、资产→存放位置→位置 | 无关系、一个关系、错误目标类型均有用例 |
| 谁可以修改资产状态？ | 项目角色与字段写权限 | 有权限成功，无权限从 API 拒绝，不只隐藏按钮 |

每个问题必须能连接到可测试的结构查询或人工操作。当前未实现的查询能力应单列，不能以图形看起来合理代替答案正确。

## 二、区分类型、对象、属性和关系

**类型**是共享定义，如“任务”；**对象**是具体记录，如“核对模型约束”；**属性**表达值，如计划日期；**关系**表达与另一个对象的具名连接，如“所属项目”。

建模卡片至少写清：稳定标识、显示名称、业务定义、反例、字段数据类型、单位、允许值、关系方向及目标类型。显示名称可以贴近业务；类型标识是引用契约，不能把改标识当成普通改名。现有对象或映射依赖标识时，必须经过兼容性校验与迁移设计。

判断规则：具有独立身份、权限、生命周期或被多个对象引用的概念，通常建成对象类型；只是一个对象的标量值，通常建成属性。把“项目状态”做枚举不会自动产生状态机；把“资产编号”设为必填不会自动提供跨对象唯一性。

W3C OWL 区分类、属性与个体，并采用开放世界语义；未知事实不能简单当作假。[OWL 2 Primer](https://www.w3.org/TR/owl2-primer/) 是语义参考，当前平台的 JSON 定义并非完整 OWL 实现。

## 三、把约束写成可执行合同

先记录规则，再说明它由哪一层执行，最后准备至少一个正例和一个反例。

| 规则 | 当前实现 | 必须保留的边界 |
| --- | --- | --- |
| 字段数据类型、必填、枚举 | 后端属性校验 | 缺失、空值与来源不完整状态不能混为同一种事实 |
| 关系目标类型 | 后端关系写入校验 | 不允许把同名而异类型对象误连 |
| `one` 关系基数 | 每个来源对象至多一个目标 | 不表示该关系必填；也不表示目标对象只能被引用一次 |
| 字段读写角色 | 服务端权限校验 | 查询、图和修改均需遵守，不以界面可见性代替授权 |
| 发布模型与旧对象兼容 | 变更集验证与发布 | 不兼容时拒绝，不能在后台悄悄丢字段 |
| 同类型组合唯一键 | 当前发布版的数据库唯一约束 | 非空完整键才占位；必填另行定义，不自动推断跨类型身份 |
| 复杂业务规则、推理 | 尚未实现 | 在方法论或页面明确写“未执行”，不能展示假通过 |

SHACL 将数据图、约束图和验证结果分开，可作为未来标准交换与约束报告的设计参考；本次没有引入 SHACL 引擎或声称标准兼容。[W3C SHACL](https://www.w3.org/TR/shacl/)

## 四、把来源映射与业务语义分开

通用入口采用“原始数据 → 结构候选 → 人工确认语义 → 发布模型 → 对象投影 → 验证业务问题”的分层流程。上传和数据库连接共用模型与映射契约；候选生成不会直接写对象或绕过发布。CSV/XLSX 的保留规则、预算和当前关系导入边界见 [数据建模入口](data-to-ontology.md)。

“从数据开始”不意味着列名就是业务定义：全表统计只描述本次文件，抽样只描述已读样本；两者都不能证明跨来源唯一性或授权业务关系。工作表行号提供的是文件内证据身份，跨文件业务身份需要独立、可审核的匹配策略。

关系匹配采用单独的“已发布关系 → 显式匹配字段 → 分类预览 → 用户确认 → 版本校验后批量写入”步骤。它可以连接上传、数据库或人工建立的有效对象，但不把物理外键、同名列或候选匹配直接认定为事实。缺值、歧义、基数冲突必须可见；部分成功须明确选择，一次性匹配不自动重连；显式保存为持续规则后按贡献归属增量维护，并保留人工支持。

字段的业务含义、来源表字段映射、具体值的原始证据是三层不同信息。业务定义不能由一个数据库列名自动决定；原始记录不得被人工纠错直接覆盖。

在现有“数据源”流程中，先发现并采样，再保存快照；在变更集中选择来源、资源、字段、转换和结构指纹。预览必须使用明确选中的快照记录，区分字段缺失、NULL、转换失败和类型冲突。抽样唯一不证明全量唯一。

来源维护字段继续只读；人工选择来源值走已有贡献裁决流程。来源删除、员工撤权、人工暂不采用分别处理，不能用“删除图上节点”替代其中任何一种。来源结构或发布模型改变后，重新检查旧映射与旧裁决。

## 五、用最小真实闭环验证模型

1. 在“本体模型 → 新建变更集”选择模板或从空白添加类型。模板只提供结构，不生成业务数据。
2. 按实际业务修改名称、定义、字段和关系；保存变更集，保留加载时的发布基线。
3. 执行验证，查看失败位置；修改后再次保存和验证。当前验证只覆盖已实现的约束，不等于所有业务规则都满足。
4. 有权限的人员审批当前修订，再发布。企业模式默认要求当前修订作者以外的审核者，发布时重新检查审批资格；本机学习保留单人模式。Action 的审批仍是独立机制。
5. 在“业务对象”创建合成测试记录，再建立具名关系；至少试一次非法枚举、错误目标类型和过期版本写入。
6. 在“图谱探索”分别查看模型与实例，选择节点核对字段，选择关系核对方向，再通过对象表单完成一次修改。
7. 刷新或重新登录，检查数据来自后端持久化；保留浏览器、API 和数据库证据，不能只演示内存数据。

当前新增两个原创模板：`project_delivery`（项目与任务）和 `asset_locations`（资产与位置），定义位于 `backend/ontology/modeling/templates.py`。入口 `GET /api/ontology/templates?project_id=…` 要求当前项目的 `ontology:write` 权限，不写数据库。使用模板仍通过普通 ChangeSet API 保存，已有模型或映射不提供一键替换。

## 六、把可视化作为工作工具

模型图回答“定义了什么”，实例图回答“哪些实际对象有关联”，引用图回答“这个说法来自哪里”。三种视图不能把候选关系、已发布事实和文档引用混画成同一种边。

视觉效果以可解释性为核心：稳定的类型颜色、具名有向边、选中邻域强调、渐进显示标签、可恢复的视野、可读的详情面板。缩放、筛选、布局只改变视图；编辑通过正常的对象修订或模型发布流程。图例数量必须注明是已加载授权子图，不能推算未授权全库数量。

保留现有 Sigma / Graphology，避免仅为视觉新鲜感再引入另一套图引擎。React Flow 的节点编辑、Cytoscape.js 的图布局值得研究，但不自动替换现有技术选型，也不复制项目应用代码。[React Flow](https://reactflow.dev/)、[Cytoscape.js](https://js.cytoscape.org/)

已加入平行关系的稳定曲线分道，反向关系保留自己的箭头与名称；只在布局力学中按邻接对计算一次吸引，不合并业务边。长节点名在画布边界内布局或省略，完整值在详情/列表可读。同一节点上的关系以可点击、可键盘选择的有向环线显示，逐条保留名称和 ID；模型中的同类型关系与实例自引用沿各自语义呈现。节点预算可选 100/200/500，查找与类型筛选只作用于已载入子图，不暗示覆盖全库。大列表默认收起但保持键盘访问。已有 200/500 节点的本机合成测量；现已支持授权全库搜索、邻域分页、固定节点和个人视图恢复；生产规模的实际结果及未达目标见 [企业 Beta 验证](beta-verification.md)。实现、来源与测量边界见 [图谱说明](graph.md)。

## 七、用证据推动迭代

每轮新增模型或规则都交付业务问题、模型版本、正反例、权限矩阵和可重复操作。先跑隔离库合同测试，再跑真实浏览器，最后按需求范围连接真实来源验证。测试数据必须标为合成示例。

本轮入门模板的可复用验证入口：

```powershell
.venv/Scripts/python scripts/test_backend.py backend/tests/modeling/test_templates.py -q
npm --prefix frontend test -- --maxWorkers=2 src/features/modeling/ModelStarter.test.tsx src/features/modeling/OntologyPage.test.tsx src/features/graph/GraphPage.test.tsx
npm --prefix frontend run build
node scripts/verify_model_starters.cjs
```

浏览器验证需要可用的 Playwright 与 Chromium；沿用已有开发环境，也可通过 `PLAYWRIGHT_MODULE` 指定已安装模块。脚本复用本机体验入口，启动独立临时 SQLite 与真实构建页面，生成一次性测试密码，不读取开发账号、生产数据库或飞书凭据。证据写入被 Git 忽略的 `var/reports/model-starters/`。

另可运行 `.venv/Scripts/python scripts/verify_model_starters_postgres.py`：需要已启动的 Docker 及本地 `postgres:17` 镜像，脚本不自动拉取镜像；随机凭据仅保留于进程环境，创建独立容器与受限运行角色并在结束后清理。本轮 SQLite/PG 模板专项 8 项通过；浏览器对象编辑后刷新持久化通过。这些证据限定在入门链路，不能替代真实外部集成或全量发布验收。无需开发环境凭据的使用入口见 [首次建模指南](getting-started.md)。
